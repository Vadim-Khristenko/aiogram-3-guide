## Термінологія {: id="glossary" }

Введемо деякі терміни, щоб надалі не плутатися:

* ПП — приватні повідомлення, у контексті бота це діалог один-на-один з користувачем, а не група/канал.
* Чат — загальна назва для ПП, груп, супергруп і каналів.
* Оновлення — будь-яка подія з [цього списку](https://core.telegram.org/bots/api#update): 
повідомлення, редагування повідомлення, колбек, інлайн-запит, платіж, додавання бота в групу тощо. 
* Хендлер — асинхронна функція, яка отримує від диспетчера/роутера чергове оновлення 
і обробляє його.
* Диспетчер — об'єкт, що займається отриманням оновлень від Telegram з подальшим вибором хендлера 
для обробки отриманого оновлення.
* Роутер — аналогічно диспетчеру, але відповідає за підмножину множини хендлерів. 
* Фільтр — вираз, який зазвичай повертає True або False і впливає на те, чи буде викликаний хендлер.
* Мідлвеар — прошарок, який втручається в обробку оновлень. 

## Встановлення {: id="installation" }

На момент написання цього розділу (2026 рік) популярним пакетним менеджером для Python-додатків 
є [uv](https://docs.astral.sh/uv/), демонстраційні проекти на GitHub поступово переводяться на нього. 

Якщо ви завантажили наявний проект, який уже використовує `uv`, то все, що потрібно зробити, — це виконати `uv sync`, 
пакетний менеджер самостійно завантажить потрібну версію Python при необхідності й встановить усі пакети 
з `pyproject.toml`, однак якщо ви створюєте проект з нуля, то виконайте послідовно наступні команди:

```bash
uv init --python 3.14
uv add aiogram
uv run python -c "import aiogram"
```

Як версію Python можна вказати будь-яку актуальну, яка отримала хоча б одне-два патч-виправлення 
(наприклад, `3.14.2` або `3.15.1`). Якщо після `uv run python -c "import aiogram"` у терміналі не було помилок, 
значить, ви все встановили правильно.


## Перший бот {: id="hello-world" }

!!! warning "Асинхронне програмування в Python"
    aiogram — це асинхронна бібліотека, тому дальше без досвіду роботи з asyncio буде складно.  
    Чудовий туторіал про асинхронність доступний 
    [на сайті Python](https://docs.python.org/3/library/asyncio-task.html).

У навчальних цілях напишемо найпростішого однофайлового бота, щоб зрозуміти, що таке aiogram і як відбувається взаємодія користувача з ботом. Відразу попереджу: тримати весь код в одному файлі дуже швидко стає поганою ідеєю, але добре підійде в двох випадках: демонстраційний код і одноразовий бот, наприклад, щоб швидко щось перевірити. Так чи інакше, далі в цьому розділі напишемо вже більш продвинутого бота з нормальною файловою структурою.

У нашому першому боті буде всього один обробник: на будь-яке повідомлення він буде відправляти легендарне "Hello world!". Що взагалі являє собою обробник (хендлер)? Це **асинхронна функція**, яка отримує на вхід 
об'єкт якої-небудь події від Telegram (повідомлення, колбек тощо) і щось з цією подією робить. 
Щоб aiogram знав, що така-то функція заявляє себе як обробник події, її потрібно зареєструвати, 
тобто якось привязати до aiogram. Але привязка відбувається не до самого фреймворку, а до окремого об'єкта в ньому – **диспетчера**. 

Створіть у каталозі проекту файл `single_file_bot.py` з наступним вмістом:

```python title="single_file_bot.py"
import asyncio                           # [1]
from os import getenv                    # [1]

from aiogram import Bot, Dispatcher      # [1]
from aiogram.types import Message        # [1]

dp = Dispatcher()                        # [2]


@dp.message()                            # [3]
async def any_message(                   # [4]
        message: Message,                # [5]
):
    await message.answer("Hello world!") # [6]


async def main():
    token = getenv("BOT_TOKEN")          # [7]
    if not token:                        # [7]
        error = "No token provided"      # [7]
        raise ValueError(error)          # [7]
    bot = Bot(token=token)               # [8]

    print("Starting bot...")
    try:
        await dp.start_polling(bot)      # [9]
    finally:
        print("Bot stopped")


if __name__ == '__main__':
    asyncio.run(main())
```

Дуже компактний код, і в майже кожному рядку закладена логіка. Цифрами в коментарях позначені:

1. Імпорти. `asyncio` обов'язковий для запуску, `getenv` дозволить прочитати токен зі змінних середовища. З імпортів із aiogram: перші два (`Bot`, `Dispatcher`) обов'язкові, останній (`Message`) потрібний лише для типізації та підказок в IDE. 
Дуже рекомендую не нехтувати типізацією, це спрощує як написання коду, так і його читання та підтримку.
2. Створення об'єкта диспетчера. У цьому прикладі він створюється на рівні всього модуля, оскільки на нього далі буде зареєстрований хендлер.
3. Декоратор, який читається як «функція під цим декоратором зареєстрована в диспетчері для обробки 
оновлень типу `Message` (оновлення лежить у полі `message` у класу `Update` оновлення, яке приходить від Telegram)».
4. Оголошення функції, яка буде обробляти оновлення типу `Message`.
5. Параметр, у якому при виклику функції буде лежати тіло оновлення (у даному випадку – типу `Message`). 
У хендлерів **завжди** є як мінімум один параметр (може бути більше), а тип значення цього параметра залежить від того, на який тип 
зареєстрована функція.
6. Бізнес-логіка хендлера. У даному випадку з цього обробника відправляється повідомлення в той же чат, де прийшла вихідна подія. Детальніше про відправку повідомлень поговоримо в наступному розділі.
7. Читання токена зі змінної середовища `BOT_TOKEN`. Якщо змінна не задана або в ній лежить пусте значення, викидаємо помилку.
8. Створення об'єкта бота з раніше отриманим токеном.
9. Запуск бота в режимі поллінгу.

Запустіть бота, передавши як змінну середовища реальний токен, отриманий у `@BotFather`. Ви повинні побачити повідомлення про старт і сам бот на будь-яке повідомлення буде надсилати текст "Hello world!":

```
$ BOT_TOKEN=1234567890:AaBbCcDdEeFfGrOoShAHhIiJjKkLlMmNnOo uv run single_file_bot.py
```

## Каркас бота {: id="file-structure" }

За роки роботи з Telegram Bot API у мене вироблявся певний стиль написання коду в цілому й телеграм-ботів 
зокрема, тому код у розділах будуватиметься саме на ньому. Тут важливо відзначити, що ідеалу не існує 
й ви вільні оформлювати свої вихідники як угодно, особливо якщо цей код нікому більше показувати не будете. 

Ось, наприклад, як виглядає спрощена структура файлів мого типового бота:

```
.
├── README.md
├── alembic
│   └── <файли з міграціями>
├── alembic.ini
├── bot
│   ├── __init__.py
│   ├── __main__.py
│   ├── config.py
│   ├── db
│   │   └── <різні файли>
│   ├── handlers
│   │   ├── __init__.py
│   │   └── <різні файли>
│   ├── i18n
│   │   └── <різні файли>
│   ├── logging_config.py
│   └── middlewares
│       ├── __init__.py
│       └── <різні файли>
├── settings.example.toml
├── settings.toml
├── pyproject.toml
└── uv.lock
```

Вище я опустив різні службові файли й каталоги, наприклад, `Makefile`, каталог `deploy` зі скриптами 
для розгортання додатка на сервері, тести й інше. Поговоримо про те, що залишилося на структурі:

`config.py`: тут описана конфігурація бота: токени, DSN для підключення до бази даних, параметри логів, 
різні зовнішні API-ключі тощо. В останні роки я переважно використовую формат TOML для зберігання налаштувань, 
у нього немає «хвороби відступів», властивої YAML, дані легко групуються за секціями, 
й сам формат вважається «рідним» у Python 3.12+. Але оскільки в мої open-source проекти періодично приходили 
коментатори з питанням, як запустити моїх ботів, маючи з конфігурованих параметрів лише змінні середовища, 
я тепер додаю fallback у вигляді підтримки env vars у свій код. Наприклад, якщо в `settings.toml` написано:

```toml
[bot]
token = "1234567890:AaBbCcDdEeFfGrOoShAHhIiJjKkLlMmNnOo"
```

То вказати те саме значення без TOML-файлу, але через змінні середовища можна так:

```
# подвійне підкреслення як розділювач задано в config.py
BOT__TOKEN=1234567890:AaBbCcDdEeFfGrOoShAHhIiJjKkLlMmNnOo
```

`logging_config.py`: для логування я давно використовую [structlog](https://www.structlog.org/en/stable/), тому що 
JSON-логи – це дуже зручно й дозволяє парсити значення автоматизованими засобами. 
У своїх ботах я збираю як логи, так і різні метрики з винятками, все це потім улітає в окрему систему, 
але розмова зараз не про неї. Я не використовую OpenTelemetry прямо, тому що в моїй парадигмі додаток не повинен знати, 
хто й як за ним спостерігає, він лише повинен «виплювати» назовні логи й метрики, а вже хто їх підбере, не так і важливо.

`handlers`: каталог, де лежать хендлери, тобто обробники подій від Telegram. Деякі хендлери згруповані в один файл, деякі настільки складні, що для них виділяється окремий `py`-файл. У `__init__.py` зазвичай імпортую всі розташовані поруч файли хендлерів і кладу функцію `get_routers()`, яка збирає ієрархію роутерів. Приклад з одного з моїх проектів:

```python
from aiogram import F, Router

from . import start, errors, admin


def get_routers(
        admins_list: list[int],
) -> list[Router]:

    admin.router.message.filter(F.from_user.id.in_(admins_list))

    return [
        start.router,
        errors.router,
        admin.router,
    ]
```

Аналогічним чином влаштовані каталоги `filters` і `middlewares`, якщо в проекті потрібні фільтри й мідлвери відповідно.

`i18n`: каталог для різних локалей (i18n – скорочення від internationalization). Тут лежать переводи різних рядків бота 
на різні мови й обгортка для роботи зі рядками через [Mozilla Fluent](https://projectfluent.org/python-fluent/).

`settings.toml` і `settings.example.toml`: файл з реальними («продовими») налаштуваннями й файл з заглушками. Перший завжди лежить у `.gitignore` й ніколи не покидає межі комп'ютера, на якому був створений, другий обов'язково коммітиться в git. Приклад такого файлу-шаблону з одного з моїх проектів:

```toml
[bot]
token = "1234567890:AaBbCcDdEeFfGrOoShALlMmNnOoPpQqRrSs"
max_quote_len = 2000
admins = [1234567]

[logs]
project_name = "some_bot"
show_datetime = true
datetime_format = "%Y-%m-%d %H:%M:%S"
show_debug_logs = true
time_in_utc = false
use_colors_in_console = false
renderer = "json"
allow_third_party_logs = true
```

`__main__.py`: точка входу. Тут читаються всі конфігураційні дані, налаштовується бот, підключення до баз даних, 
ініціалізація інших коннекторів і запускається отримання даних поллінгом або налаштовується вебхук. 
А бот легко запускається як `uv run -m bot` (без `uv` це було б `python -m bot` у активованому Venv). 

Не лякайтеся такого складного опису, насправді все виглядає досить просто, а якісь куски коду можна спокійно 
в незмінному вигляді копіювати з проекту в проект. Зараз підготуємо каркас вашого першого бота.

У каталозі, де ви раніше ініціалізували `uv`-проект, створіть наступну структуру з пустими файлами (не чіпайте `pyproject.toml` і `uv.lock`):

```
bot
├── __init__.py
├── __main__.py
├── config.py
├── handlers
│   ├── __init__.py
│   └── start.py
└──logging_config.py
settings.example.toml
settings.toml
pyproject.toml
uv.lock
```

Додатково встановіть кілька бібліотек, які знадобляться для роботи з конфігурацією й логами:

```shell
uv add pydantic-settings structlog
```

Якщо каталог є частиною git-репозиторію, то обов'язково додайте `settings.toml` в `.gitignore`. Вміст файлів 
`config.py` і `logging_config.py` візьміть з каталогу 
[01_quickstart](https://github.com/MasterGroosha/aiogram-3-guide/tree/master/code/01_quickstart) з git-репозиторію 
до цієї книги. Далі поговоримо вже безпосередньо про бізнес-логіку.


## Другий бот {: id="second-bot" }

Поставимо мету на цей розділ: написати бота, який буде на команду `/start` відповідати «Привіт!», 
а на будь-який інший введення відповідати «Я тебе не розумію». Почнемо з більш широкого, тобто з обробника «будь-якого повідомлення». 

Коли диспетчер отримує подію від Telegram, перед ним постає завдання вибрати, який із зареєстрованих хендлерів буде займатися його обробкою. 
Для цього диспетчер по черзі перевіряє кожен хендлер на відповідність якомусь ознакам – **фільтру**. 
Якщо умова у фільтрі повертає True, то диспетчер передає подію (оновлення) хендлеру й на цьому все. 
Якщо фільтр повернув False, то диспетчер пробує наступний хендлер і так далі, поки обробники не закінчаться. 
Робимо наступні важливі висновки:

!!! info ""
    • Хендлер забезпечує обробку події від Telegram.  
    • Хендлер повинен бути зареєстрований у диспетчері.  
    • Диспетчер вибирає хендлери по черзі, перевіряючи фільтри кожного хендлера.  
    • Диспетчер передає оновлення першому хендлеру, чий фільтр повернув True. Якщо таких нема, то оновлення не дається нікому.  

Оскільки диспетчер існує в єдиному екземплярі, тягти його з файлу в файл для реєстрації хендлерів 
може бути затруднительно й легко призводить до циклічних залежностей: `file_1` імпортує код із `file_2` для реєстрації хендлера, у `file_2` імпортується диспетчер із `file_1` -> циклічний імпорт, помилка. Для вирішення цієї проблеми існують **роутери**. Роутер – це об'єкт, до якого реєструються хендлери, а далі роутер реєструється у диспетчері. Більше того, можна поставити фільтр не тільки на хендлер, але й на роутер, тоді, якщо оновлення не прошло фільтр роутера, то жоден хендлер роутера перевіряватися не буде. Із цього робимо ще кілька висновків:

!!! info ""
    • Хендлери привязуються до диспетчера явно (прямо) або неявно (через роутер).  
    • Роутер об'єднує в собі один або кілька хендлерів.  
    • **Диспетчер – це кореневий роутер**.  
    • Фільтри можна ставити як на хендлери, так і на роутер цілком.  

Більш докладно фільтри, а також ще одна не описана вище сутність – мідлвери – будуть розглядатися в наступних розділах.

Таким чином, при проектуванні бізнес-логіки завдання програміста – правильно організувати ієрархію хендлерів, щоб для обробки оновлення вибирався саме бажаний хендлер, а не якийсь інший.

Скопіюйте в файл `bot/handlers/start.py` наступний код:

```python title="bot/handlers/start.py"
from aiogram import Router                       # [1]
from aiogram.types import Message                # [1]

router = Router(name="start")                    # [2]


@router.message()                                # [3]
async def any_message(
        message: Message,
) -> None:
    await message.answer("Я тебе не розумію")
```

Перед вами дуже простий роутер з одним хендлером. Цифрами вище позначені:

1. Імпорти. Перший (`Router`) обов'язковий, другий (`Message`) потрібний лише для типізації й підказок в IDE. 
2. Створення екземпляра роутера. Необов'язковий параметр `name` задає ім'я роутера, але це ні на що не впливає.
3. Декоратор тепер навішується не на диспетчер, а на роутер.

За ТЗ у нас повинно бути два хендлери, давайте тепер додамо другий. У цей раз можна все покласти в один роутер, оскільки код невеликий і обидва обробники в цілому подібні. Але де розмістити хендер – вище або нижче функції `any_message`? Зараз у існуючого хендлера немає ніяких фільтрів, крім того, що хендлер спрацьовує на оновлення типу `Message`. Оскільки наш майбутній хендлер на команду `/start` більш вузькоспеціалізований, має сенс його додати вище по коду, щоб він був зареєстрований раніше. У такому разі спочатку диспетчер/роутер перевірить хендлер на відповідність фільтру «це команда `/start`», а якщо ні, то перевірить наступний фільтр «будь-яке повідомлення», який завжди повернує True.

Замініть повністю вміст файлу `start.py` наступним вмістом:

```python title="bot/handlers/start.py"
from aiogram import Router
from aiogram.filters import CommandStart    # [1]
from aiogram.types import Message

router = Router(name="start")


@router.message(CommandStart())             # [2]
async def cmd_start(
        message: Message,
) -> None:
    await message.answer("Привіт!")


@router.message()                           # [3]
async def any_message(
        message: Message,
) -> None:
    await message.answer("Я тебе не розумію")
```

Звернемо увагу на наступні моменти:

1. Додано імпорт фільтра `CommandStart`. Він, як видно з назви, повернути True, якщо повідомлення є командою `/start`. Для будь-яких інших команд є загальний фільтр `Command`, його ви побачите в наступних розділах.
2. Вищезгаданий фільтр вішається на хендлер `cmd_start()`.
3. Старий хендлер залишається незайманим: нема потреби для `any_message()` створювати окремий фільтр «все, що не є командою `/start`», оскільки при спрацюванні хендлера `cmd_start()` інші хендлери перевіряватися не будуть.

Невелике відступлення: зрідка бувають ситуації, коли фільтр є динамічним, тобто конкретні його 
параметри невідомі до моменту запуску самого бота. У такому разі реєструвати хендлери надо не через декоратор, 
а через метод `register()` роутера або диспетчера. Тоді б файл `start.py` виглядав трохи інакше:

```python title="bot/handlers/start.py"
from aiogram import Router
from aiogram.filters import CommandStart
from aiogram.types import Message

router = Router(name="start")


async def cmd_start(
        message: Message,
) -> None:
    await message.answer("Привіт!")


async def any_message(
        message: Message,
) -> None:
    await message.answer("Я тебе не розумію")


# Де-небудь нижче у цьому файлі, можливо, всередину якої-то функції:
router.message.register(cmd_start, CommandStart())
router.message.register(any_message)
```

Роутер створений, хендлери теж. Хендлери привязані до роутера, але сам роутер поки ні до чого не привязаний. 
Давайте для початку зберемо ієрархію роутерів (він у нас один, але все ж). Для цього в `bot/handlers/__init__.py` 
впишіть наступний код:

```python title="bot/handlers/__init__.py"
from aiogram import Router

from . import (
    start,
)


def get_routers() -> list[Router]:
    return [
        start.router,
    ]
```

Тут все просто: імпортуємо всі файли з хендлерами з `bot/handlers` і повертаємо список роутерів у потрібному порядку, 
саме в такому порядку їх буде перевіряти диспетчер. А що й сам диспетчер? Його створимо в `bot/__main__.py` разом зі всіма іншими об'єктами й запуском бота:

```python title="bot/__main__.py"
import asyncio

import structlog
from structlog.typing import FilteringBoundLogger

from aiogram import Bot, Dispatcher
from bot.config import Settings
from bot.handlers import get_routers
from bot.logging_config import get_structlog_config

logger: FilteringBoundLogger = structlog.get_logger()

async def main() -> None:
    # Читання конфігурації (toml-файл або env vars – не важливо)
    settings = Settings()
    # Конфігурування логгера
    structlog.configure(**get_structlog_config(settings.logs))

    # Створення об'єкта бота. Обов'язковий аргумент token – читаємо токен 
    # із конфігурації. Оскільки токен помічено як SecretStr, то необхідно 
    # додатково викликати get_secret_value().
    bot = Bot(
        token=settings.bot.token.get_secret_value(),
    )

    # Створення об'єкта диспетчера й привязка роутерів
    dp = Dispatcher()
    # Невеликий лайфхак: include_routers() приймає на вхід 
    # довільну кількість аргументів
    # get_routers() повертає список: [A, B, C,...]
    # й цей список буде переданий як набір аргументів:
    # include_routers(A, B, C,...)
    dp.include_routers(*get_routers())

    # Запуск бота в режимі поллінгу
    await logger.ainfo("Starting polling...")
    try:
        await dp.start_polling(bot)
    finally:
        await logger.ainfo("Bot stopped")


asyncio.run(main())
```
